# Приложение: Справочники

## Зачем это нужно?

Этот раздел содержит справочную информацию: глоссарий терминов, чек-листы, шаблоны SOP и таблицы решений. Используйте его как справочник при работе над проектами.

## Глоссарий

### Основные концепции

**Agent (Агент)** — система, использующая LLM в качестве "движка рассуждений" для восприятия окружения, принятия решений и выполнения действий. Состоит из: LLM (мозг) + Tools (руки) + Memory (память) + Planning (планирование).

**См. также:** [Глава 00: Предисловие](../00-preface/README.md#что-такое-ai-agent)

**Runtime (Среда выполнения)** — код агента, который вы пишете на Go. Связывает LLM с инструментами и управляет циклом работы агента. Выполняет парсинг ответов LLM, валидацию, выполнение инструментов и управление историей диалога.

**Важно:** Runtime — это не отдельная система или фреймворк. Это ваш код в `main.go` или отдельных модулях.

**См. также:** [Глава 09: Анатомия Агента](../09-agent-architecture/README.md#runtime-среда-выполнения)

**Tool (Инструмент)** — функция Go, API-вызов или команда, которую агент может выполнить для взаимодействия с реальным миром. Описывается в формате JSON Schema и передается модели в поле `tools[]`.

**Синонимы:** Function (в контексте Function Calling)

**См. также:** [Глава 03: Инструменты и Function Calling](../03-tools-and-function-calling/README.md)

**Tool Call / Function Call (Вызов инструмента)** — структурированный JSON-запрос, который LLM генерирует для вызова инструмента. Содержит имя инструмента и аргументы в формате JSON. Возвращается в поле `tool_calls` ответа модели.

**Примечание:** "Tool Call" и "Function Call" — это одно и то же. "Function Calling" — название механизма в API, "Tool Call" — конкретный вызов инструмента.

**См. также:** [Глава 03: Инструменты и Function Calling](../03-tools-and-function-calling/README.md#шаг-3-ответ-модели-tool-call)

**MCP (Model Context Protocol)** — протокол подключения инструментов и данных к LLM-агентам (Anthropic). Предоставляет стандартный интерфейс для Resources, Tools и Prompts.

**Artifact / artifact_id (Артефакт)** — большой результат инструмента (файл, лог, JSON, HTML и т.д.), который рантайм сохраняет вне `messages[]`, а в контекст модели возвращает только короткий excerpt + `artifact_id`. Это снижает стоимость/latency и уменьшает риск переполнения контекста.

**См. также:** [Глава 20: Cost & Latency Engineering](../20-cost-latency-engineering/README.md)

**AgentState (Состояние агента)** — состояние хода, живущее ВНЕ контекста LLM: цель, ограничения (в т.ч. HITL), бюджеты, план, артефакты (файлы/БД + пути/ID). Контекст агента — линейная история сообщений; «известные факты» и прочие структуры внутрь контекста не селектируются (см. [Главу 11](../11-state-management/README.md)).

**Risk Level (Уровень риска)** — классификация сайд-эффектов инструмента, которую использует политика и HITL-гейты. Единая шкала курса: `read_only` (авто) / пишущие локально (Confirm по политике) / деструктивные или внешние (dry-run + Confirm + `confirmed_by`). См. [Главу 05](../05-safety-and-hitl/README.md).

**ReAct Loop (Цикл Рассуждения и Действия)** — паттерн работы автономного агента: Reason (рассуждает) → Act (действует) → Observe (наблюдает) → повторяет. Агент анализирует ситуацию, выполняет действие, видит результат и решает, что делать дальше. В современном виде «рассуждение» — это обычный content модели рядом с tool_calls, отдельный текстовый формат не нужен.

**Этимология:** ReAct = Reason + Act

**См. также:** [Глава 04: Автономность и Циклы](../04-autonomy-and-loops/README.md#react-loop-цикл-автономности)

**Skills (Навыки)** — переиспользуемые модули знаний агента в формате SKILL.md (agentskills.io): директория с инструкциями и скриптами. В system prompt попадают только названия/описания (~1 строка на скил — progressive disclosure), текст скила модель читает сама инструментом `read`, когда он нужен. Подробнее — [Глава 09](../09-agent-architecture/README.md#skills-навыки).

### LLM и контекст

**Context Window (Контекстное окно)** — максимальное количество токенов, которые модель может обработать за один запрос. Ограничивает размер истории диалога. У современных моделей (GLM-5.3, Fable 5.1, Opus 5.5) — от ~128k до ~1M токенов; точное значение смотрите в документации провайдера, оно меняется чаще, чем переиздаются книги.

**См. также:** [Глава 01: Физика LLM](../01-llm-fundamentals/README.md#контекстное-окно-context-window)

**Token (Токен)** — единица текста, которую обрабатывает модель. Один токен ≈ 0.75 слова (английский) или ≈ 1.5 токена на слово (русский). Все, что агент "знает" о текущей задаче, ограничено количеством токенов в контекстном окне.

**См. также:** [Глава 01: Физика LLM](../01-llm-fundamentals/README.md#что-такое-токен)

**System Prompt (Системный промпт)** — инструкции для модели, которые задают роль, цель, ограничения и процесс работы агента. Передается в `messages[0].content` с ролью `"system"`. Состоит из: Role (Persona), Goal, Constraints, Format, SOP.

**См. также:** [Глава 02: Промптинг](../02-prompt-engineering/README.md#структура-system-prompt)

**Temperature (Температура)** — параметр энтропии распределения вероятностей токенов. Настройка качества/разнообразия генерации: низкие значения (0.0–0.3) уменьшают разброс, высокие — увеличивают.

**Правило:** для агентных циклов и структурированных вызовов типично `0.0–0.3`. Но помните: температура — не «выключатель детерминизма». У многих провайдеров `T=0` технически не гарантирует greedy-детерминизм (батчинг, MoE); воспроизводимость процесса агента дают структура (JSON Schema, валидация), гарды в коде и evals.

**См. также:** [Глава 01: Физика LLM](../01-llm-fundamentals/README.md#температура-temperature)

**Prompt Cache (Кэш промпта)** — оптимизация на стороне провайдера LLM: одинаковый префикс `messages[]` (system prompt + первые сообщения) кэшируется и оплачивается со скидкой 50–90%. Чтобы попадать в кэш, префикс должен быть **байт-в-байт стабилен** между запросами одного агентского run. Любая мутация system prompt (вставка времени, динамических фактов) или замена ранних сообщений выбивает кэш — итерации становятся в разы дороже и медленнее. Поэтому динамическое состояние (текущее время, факты) кладут в **последнее** user-сообщение или в результаты tools, а не в `messages[0]`.

**Правило:** `messages[0]` (system prompt) — append-only и не мутируется внутри одного run.

**См. также:** [Глава 12: Системы Памяти Агента](../12-agent-memory/README.md), [Глава 13: Context Engineering](../13-context-engineering/README.md)

### Техники промптинга

**Chain-of-Thought (CoT)** — техника промптинга "думай по шагам", заставляющая модель генерировать промежуточные рассуждения перед финальным ответом. Критична для агентов, решающих сложные многошаговые задачи.

**См. также:** [Глава 02: Промптинг](../02-prompt-engineering/README.md#chain-of-thought-cot-думай-по-шагам)

**Few-Shot Learning / Few-Shot (Обучение с примерами)** — техника промптинга, при которой в промпт добавляются примеры желаемого поведения. Модель адаптируется к формату на основе примеров в контексте.

**Антоним:** Zero-Shot (только инструкция, без примеров)

**См. также:** [Глава 02: Промптинг](../02-prompt-engineering/README.md#few-shot-инструкция--примеры)

**Zero-Shot Learning / Zero-Shot (Обучение без примеров)** — техника промптинга, при которой модели дается только инструкция без примеров. Экономит токены, но требует точных инструкций.

**Антоним:** Few-Shot (с примерами)

**См. также:** [Глава 02: Промптинг](../02-prompt-engineering/README.md#zero-shot-только-инструкция)

**In-Context Learning (ICL)** — способность модели адаптировать поведение на основе примеров внутри промпта, без изменения весов модели. Работает в режимах Zero-shot и Few-shot.

**См. также:** [Глава 02: Промптинг](../02-prompt-engineering/README.md#in-context-learning-icl-zero-shot-и-few-shot)

**SOP (Standard Operating Procedure)** — алгоритм действий, закодированный в промпте. Задает последовательность шагов для решения задачи. CoT помогает следовать SOP шаг за шагом.

**См. также:** [Глава 02: Промптинг](../02-prompt-engineering/README.md#sop-и-декомпозиция-задач-процесс-агента)

### Память и контекст

**Memory (Память агента)** — набор механизмов, которые позволяют агенту удерживать и использовать информацию. В курсе разделяется **по горизонту**, а не по «уровням»:

- **Внутри Run** — линейный `messages[]` в контексте LLM + при необходимости один `condense`. Всё в оперативной памяти, живёт до конца Run.
- **Между Run-ами в одной сессии** — session-level state (план, прочитанные файлы, последние действия), который передаётся между итерациями REPL.
- **Между сессиями** — долговременная память, которой агент управляет сам через tools (`search_memory` / `read_note` — чтение; запись фактов — в store); хранится в БД/файлах.

Никакой отдельной «кратковременной памяти» как структуры нет — её роль играет сам `messages[]`.

**См. также:** [Глава 12: Системы Памяти Агента](../12-agent-memory/README.md)

**Working Memory (Рабочая память)** — в курсе этим словом называются **две разные вещи**, не путайте:

1. **LLM-контекст внутри одного Run** — это просто **линейный `messages[]`** (system + диалог + tool results) до ближайшего `condense`. Никаких «слоёв» (Working/Summary/Facts) поверх — это устаревший паттерн, см. гл. 13 и [Lab 11](https://github.com/kshvakov/ai-agent-course/tree/main/translations/ru/labs/lab11-memory-context).
2. **Session-level state** — план, прочитанные файлы, последние действия, которые переживают между REPL-циклами. Это не LLM-контекст, а структура, которая сериализуется на диск и загружается при рестарте. См. гл. 11.

**См. также:** [Глава 11: State Management](../11-state-management/README.md), [Глава 12: Системы Памяти Агента](../12-agent-memory/README.md), [Глава 13: Context Engineering](../13-context-engineering/README.md)

**Long-term Memory (Долговременная память)** — постоянное хранилище между сессиями: факты, предпочтения, прошлые решения. **Принцип из этого курса:** агент управляет долговременной памятью **сам** через tools (`search_memory` / `read_note` — чтение по требованию; запись — факты в store), а не через авто-извлечение фактов из каждого сообщения и не через мутацию system prompt. Хранится в БД/файлах; для большого корпуса — векторный поиск (RAG).

**См. также:** [Глава 12: Системы Памяти Агента](../12-agent-memory/README.md#долговременная-память-между-сессиями), [Lab 11](https://github.com/kshvakov/ai-agent-course/tree/main/translations/ru/labs/lab11-memory-context)

**Episodic Memory (Эпизодическая память)** — память о конкретных событиях: «пользователь спрашивал о месте на диске 2026-01-06». Для большинства агентов это просто записи с датой в store долговременной памяти — отдельная инфраструктура не нужна. Полезна для отладки.

**См. также:** [Глава 12: Системы Памяти Агента](../12-agent-memory/README.md)

**Semantic Memory (Семантическая память)** — общие знания об окружении/пользователе («предпочитает JSON ответы»). В практике — те же записи в долговременной памяти, просто более обобщённые. Отдельного «семантического хранилища» делать не нужно.

**См. также:** [Глава 12: Системы Памяти Агента](../12-agent-memory/README.md)

**Context Engineering (Управление контекстом)** — техники эффективного управления контекстом: подсчёт токенов через `usage.PromptTokens`, единый порог сжатия (~0.85 контекстного окна), однократный `condense` за run, защита `tool_call ↔ tool_result` пар при усечении.

**См. также:** [Глава 13: Context Engineering](../13-context-engineering/README.md)

**Condense (Сжатие истории)** — операция on-demand суммаризации старой части `messages[]` через отдельный LLM-вызов, чтобы освободить место в контекстном окне. Триггерится одним порогом (`usage.PromptTokens > contextWindow * 0.85` или реактивно на `ContextOverflowError`). Принципы корректного `condense`: (1) **кэшируемый префикс (system + блок tools) не меняется** — суммаризируется только head-часть истории, иначе теряется prompt cache; (2) `safeTail` сохраняет `tool_call ↔ tool_result` пары — нельзя оставить tool_call без своего tool_result или наоборот; (3) лимит — один `condense` за run, иначе ходит по кругу. Compact-копий и recall-каталогов блоков курс не рекомендует (анти-паттерн, см. [Главу 12](../12-agent-memory/README.md)).

**См. также:** [Глава 13: Context Engineering](../13-context-engineering/README.md), [Lab 09](https://github.com/kshvakov/ai-agent-course/tree/main/translations/ru/labs/lab09-context-optimization), [Lab 11](https://github.com/kshvakov/ai-agent-course/tree/main/translations/ru/labs/lab11-memory-context)

**RAG (Retrieval Augmented Generation)** — техника дополнения контекста агента релевантными документами из базы знаний через векторный поиск. Документы разбиваются на чанки, преобразуются в векторы (embeddings), при запросе ищутся похожие векторы.

**См. также:** [Глава 06: RAG и База Знаний](../06-rag/README.md)

**Agentic RAG** — RAG, встроенный в Agent Loop. Агент сам решает, когда и где искать, оценивает качество результатов и может искать повторно.

**Self-RAG** — RAG с самооценкой качества. Модель оценивает релевантность найденных документов и решает: ответить, уточнить запрос или искать ещё.

**Hybrid Search (Гибридный поиск)** — комбинация keyword-поиска (BM25) и векторного поиска. Объединяет результаты через Reciprocal Rank Fusion.

### Планирование и архитектура

**Planning (Планирование)** — способность агента разбить сложную задачу на последовательность простых шагов и выполнить их в правильном порядке. Уровни: имплицитное (ReAct), явное (Plan-and-Solve), иерархическое.

**См. также:** [Глава 09: Анатомия Агента](../09-agent-architecture/README.md#planning-планирование)

**State Management (Управление состоянием)** — управление состоянием выполнения задачи: прогресс, что сделано, что ожидает, возможность возобновления. Включает идемпотентность инструментов, retries с экспоненциальным backoff, дедлайны, persist state.

**См. также:** [Глава 11: State Management](../11-state-management/README.md)

**Checkpoint (Контрольная точка)** — снимок состояния агента в определённый момент. Позволяет восстановить работу после сбоя без потери прогресса.

**Reflexion (Рефлексия)** — техника самокоррекции агента через анализ ошибок. Цикл: Act → Observe → Fail → REFLECT → Plan Again. Агент анализирует, почему действие не сработало, и планирует заново.

**См. также:** [Глава 09: Анатомия Агента](../09-agent-architecture/README.md#reflexion-самокоррекция)

### Безопасность и надежность

**Junior-Employee Model (Ментальная модель «агент — это новый сотрудник»)** — базовая рамка из Предисловия: agent = новый стажёр, начитанный и быстрый, но без вашего контекста и без чувства последствий. Большинство правил security/governance — это перевод обычных HR-практик (роль, доступы, апрув старшего, аудит, испытательный срок) на язык кода. **Четыре асимметрии** делают агента опаснее человека на той же роли: (1) скорость 1000×, (2) параллелизм по N сессий, (3) отсутствие психологического тормоза при разрушающих действиях, (4) prompt injection как социальная инженерия через данные. Под эти асимметрии добавляются rate-limit, max parallel tools, idempotency, sanitization внешних данных.

**См. также:** [Предисловие → Ментальная модель](../00-preface/README.md#ментальная-модель-агент--это-новый-сотрудник), [Глава 17: Security и Governance](../17-security-and-governance/README.md)

**Blast Radius (Радиус поражения)** — масштаб последствий ошибочного действия агента. Минимизация blast radius — основной принцип проектирования tools: вместо `delete_files(pattern string)` лучше `move_to_trash(paths []string)` с явным списком; вместо `run_sql(query string)` лучше `select_users(filter UserFilter)`. Защитные слои, уменьшающие blast radius: dry-run, идемпотентность, allowlist путей/таблиц, ограничение пагинации/лимитов, обязательный HITL для разрушающих операций, sandboxing.

**См. также:** [Глава 03: Инструменты и Function Calling](../03-tools-and-function-calling/README.md), [Глава 17: Security и Governance](../17-security-and-governance/README.md)

**Recovery State Machine (Машина восстановления при ошибках)** — структурированный подход к обработке ошибок LLM-вызовов: вместо одного `if err != nil { return err }` агент классифицирует ошибку (`RateLimit`, `ContextOverflow`, `InvalidToolCall`, `ProviderUnavailable`, `MalformedJSON`) и применяет специфичную реакцию (backoff + retry, on-demand `condense`, повторный вызов с подсказкой формата, fallback на другую модель, recovery-парсер для извлечения tool calls из сырого текста). Без recovery state machine агент в проде «падает на первой кочке».

**См. также:** [Глава 11: State Management](../11-state-management/README.md), [Глава 13: Context Engineering](../13-context-engineering/README.md)

**Grounding (Заземление)** — привязка агента к реальным данным через Tools/RAG, чтобы избежать галлюцинаций. Агент должен использовать инструменты для получения фактов, а не выдумывать их.

**См. также:** [Глава 01: Физика LLM](../01-llm-fundamentals/README.md#2-галлюцинации)

**Human-in-the-Loop (HITL)** — механизм подтверждения критических действий человеком перед выполнением. Включает Confirmation (подтверждение), Clarification (уточнение), категории инструментов (риск — явной категорией, не числом).

**См. также:** [Глава 05: Безопасность и Human-in-the-Loop](../05-safety-and-hitl/README.md)

**Prompt Injection (Инъекция промпта)** — атака на агента через манипуляцию входными данными. Злоумышленник пытается "обмануть" промпт, чтобы агент выполнил нежелательное действие.

**См. также:** [Глава 05: Безопасность и Human-in-the-Loop](../05-safety-and-hitl/README.md#ошибка-3-prompt-injection)

**Defense in Depth (Глубокая защита)** — многоуровневая стратегия безопасности. Каждый слой (input validation, runtime checks, output filtering, monitoring) защищает от разных типов атак.

**Red Teaming** — систематическое тестирование агента на уязвимости. Команда "атакующих" пытается заставить агента нарушить правила.

**Eval (Evaluation)** — тест для проверки качества работы агента. Может проверять корректность ответов, выбор инструментов, следование SOP, безопасность. В промышленных системах используется в CI/CD.

**См. также:** [Глава 08: Evals и Надежность](../08-evals-and-reliability/README.md)

**DeepEval** — фреймворк для оценки качества LLM-приложений. Предоставляет метрики: faithfulness, answer relevancy, context precision.

**Multi-turn Evaluation (Многоходовая оценка)** — оценка агента в многошаговых диалогах. Проверяет связность контекста и корректность действий на каждом шаге.

**RAGAS** — фреймворк метрик для RAG-систем. Измеряет context precision, context recall, faithfulness и answer relevance.

### Мультиагентные системы

**Multi-Agent System (MAS)** — система из нескольких агентов, работающих вместе. Может использовать паттерны Supervisor/Worker, изоляцию контекста, маршрутизацию задач между специализированными агентами.

**См. также:** [Глава 07: Multi-Agent Systems](../07-multi-agent/README.md)

**A2A (Agent-to-Agent)** — протокол межагентной коммуникации (Google). Стандартизирует обмен задачами между агентами через Agent Card, Task lifecycle и Message/Artifact.

**Handoff (Передача управления)** — передача управления от одного агента другому с частью контекста. Используется при эскалации или смене домена.

**Router Agent (Агент-маршрутизатор)** — агент-маршрутизатор. Классифицирует запрос и направляет его к подходящему специалисту.

**Subagent (Под-агент)** — под-агент, создаваемый динамически для подзадачи. В отличие от Worker, создаётся "на лету" под конкретную задачу.

## Capability Benchmark (Characterization)

Перед тем как строить агентов, необходимо **научно подтвердить**, что выбранная модель обладает необходимыми способностями. В инженерии это называется **Characterization** (характеризация).

### Зачем это нужно?

Мы не верим этикеткам ("Super-Pro-Max Model"). Мы верим тестам.

**Проблема без проверки:** Вы взяли локальную instruct-модель, которая заявляет поддержку tools, и начали строить агента. Через час работы обнаружили, что модель не вызывает инструменты, а только пишет текст. Вы потратили время на отладку кода, хотя проблема была в модели.

**Решение:** Запустите capability benchmark **перед** началом работы. Это сэкономит часы.

### Что мы проверяем?

#### 1. Basic Sanity (Базовая работоспособность)
- Модель отвечает на запросы
- Нет критических ошибок API
- Базовая связность ответов

#### 2. Instruction Following (Следование инструкциям)
- Модель может жестко придерживаться ограничений
- Важно для агентов: они должны возвращать строго определенные форматы
- **Тест:** "Напиши стих, но не используй букву 'а'"
- **Зачем:** Агент должен возвращать строго определенные форматы, а не "размышления"

#### 3. JSON Generation (Генерация JSON)
- Модель может генерировать валидный синтаксис
- Все взаимодействие с инструментами строится на JSON
- Если модель забывает закрыть скобку `}`, агент падает
- **Тест:** "Верни JSON с полями name и age"

#### 4. Function Calling (Использование инструментов)
- Специфический навык модели распознавать определение функций и формировать специальный токен вызова
- Без этого невозможны инструменты (см. [Главу 03: Инструменты](../03-tools-and-function-calling/README.md))
- **Зачем:** Это основа для [Lab 02](https://github.com/kshvakov/ai-agent-course/tree/main/translations/ru/labs/lab02-tools) и всех последующих лаб

### Почему не все модели умеют Tools?

LLM (Large Language Model) — это вероятностный генератор текста. Она не "знает" про функции из коробки.

Механизм **Function Calling** — это результат специальной тренировки (Fine-Tuning). Разработчики модели добавляют в обучающую выборку тысячи примеров вида:

```
User: "Check weather"
Assistant: <special_token>call_tool{"name": "weather"}<end_token>
```

Если взять модель без fine-tune под инструкции (base model), она не видела этих примеров. Она просто продолжит диалог текстом.

**Как проверить:** Запустите [Lab 00](https://github.com/kshvakov/ai-agent-course/tree/main/translations/ru/labs/lab00-capability-check) перед началом работы с инструментами.

### Почему температура важна для агентов?

Температура регулирует "случайность" выбора следующего токена:
- **High Temp (0.8+):** Модель выбирает менее вероятные слова. Хорошо для стихов, творческих задач.
- **Low Temp (0.0–0.3):** Модель чаще выбирает наиболее вероятное слово — меньше разброс в выборе инструментов и формате вывода.

Для агентов, которые должны выдавать строгий JSON или вызов функции, нужен низкий разброс — «творческая» ошибка в JSON сломает парсер. Но детерминизм процесса обеспечивает не температура, а структура: схемы вызовов, валидация, repair ломаного JSON и гарды в коде.

**Правило:** для агентных циклов — `0.0–0.3`; надёжность добивается schema/repair/гардами, а не надеждой на `T=0`.

### Как интерпретировать результаты?

#### Все тесты прошли
Модель готова для курса. Можно продолжать работу.

#### Предупреждение: 3 из 4 тестов прошли
Можно продолжать, но с осторожностью. Возможны проблемы в краевых случаях.

#### Function Calling провален
**Критично:** Модель не подходит для [Lab 02](https://github.com/kshvakov/ai-agent-course/tree/main/translations/ru/labs/lab02-tools)-08. Нужна другая модель.

**Что делать:**
1. Возьмите модель с поддержкой tools: облачные (GLM-5.3, GLM-5.3 Flash, Fable 5.1, Opus 5.5) или локальную через Ollama/vLLM/LM Studio — любую, что заявляет function calling и даёт OpenAI-совместимый endpoint.
2. Перезапустите тесты

#### JSON Generation провален
Модель генерирует сломанный JSON (пропущенные скобки, кавычки).

**Что делать:**
1. Попробуйте другую модель
2. Или снизьте `Temperature` (0.0–0.3) и добавьте repair ломаного JSON — температура не гарантирует валидный JSON, repair гарантирует

## FAQ: Что происходит на деле?

### Q: Агент сам решает, что делать. Это магия?

**A:** Нет. Агент работает по простому алгоритму:
1. LLM видит описание инструментов в `tools[]`
2. LLM генерирует JSON с именем инструмента и аргументами
3. Ваш код (Runtime) парсит JSON и выполняет реальную функцию
4. Результат добавляется в историю
5. LLM видит результат в контексте и генерирует следующий шаг

Никакой магии тут нет — это просто цикл, где модель видит результаты предыдущих действий.

**См. также:** [Глава 04: Автономность](../04-autonomy-and-loops/README.md#магия-vs-реальность-как-работает-цикл)

### Q: Как модель "знает", какой инструмент вызвать?

**A:** Модель не "знает". Она выбирает инструмент на основе:
1. **Описания инструмента** (`Description` в JSON Schema)
2. **Запроса пользователя** (семантическое соответствие)
3. **Контекста предыдущих результатов** (если есть)

Чем точнее `Description`, тем лучше выбор.

**См. также:** [Глава 03: Инструменты](../03-tools-and-function-calling/README.md)

### Q: Модель "помнит" прошлые разговоры?

**A:** Нет. Модель stateless. Она видит прошлое только в `messages[]`, который вы передаете в каждом запросе. Если вы не передаете историю, модель ничего не помнит.

**См. также:** [Глава 01: Физика LLM](../01-llm-fundamentals/README.md#вероятностная-природа)

### Q: Почему агент иногда делает разные действия на один и тот же запрос?

**A:** Это происходит из-за вероятностной природы LLM. При высокой температуре модель выбирает менее вероятные токены. Для агентных циклов используйте низкую температуру (0.0–0.3) — но помните, что воспроизводимость процесса дают структура (schema, валидация, repair), гарды в коде и evals, а не сама по себе температура.

**См. также:** [Глава 01: Физика LLM](../01-llm-fundamentals/README.md#температура-temperature)

### Q: Модель выдумывает факты. Как это исправить?

**A:** Используйте **Grounding** (Заземление):
1. Запретите выдумывать факты в System Prompt
2. Дайте агенту доступ к реальным данным через Tools
3. Используйте RAG для доступа к документации

**См. также:** [Глава 01: Физика LLM](../01-llm-fundamentals/README.md#2-галлюцинации)

### Q: Агент "забывает" начало разговора. Что делать?

**A:** Это происходит, когда история диалога превышает размер контекстного окна. Правильное решение — **одно, простое**: `condense`.

1. Считаете токены по `usage.PromptTokens` из ответа провайдера (не свой счётчик).
2. Когда `usage.PromptTokens > contextWindow * 0.85` — делаете **один** `condense`: отдельный LLM-запрос суммаризует старую часть истории (head) с тем же кэшируемым префиксом (system + tools), tail сохраняется целиком — с защитой пар `tool_call ↔ tool_result` (`safeTail`); system prompt не меняется.
3. Один `condense` на Run; если не помогло — задачу пора делить на под-Run.

Чего **не** нужно: скоринг важности сообщений, переупорядочивание истории, адаптивные лесенки `prioritize → summarize → truncate`, слои Working/Summary/Facts, динамический system prompt. Это классические формы оверинжиниринга — дорого, хрупко, портит prompt cache.

Долговременные знания, которые должны пережить `condense`, — это уже **не контекст**, а долговременная память: агент **сам** сохраняет факты в store и читает их по требованию через `search_memory` / `read_note` ([гл. 12](../12-agent-memory/README.md)).

**См. также:** [Глава 12: Системы Памяти Агента](../12-agent-memory/README.md), [Глава 13: Context Engineering](../13-context-engineering/README.md), [Lab 09](https://github.com/kshvakov/ai-agent-course/tree/main/translations/ru/labs/lab09-context-optimization), [Lab 11](https://github.com/kshvakov/ai-agent-course/tree/main/translations/ru/labs/lab11-memory-context)

### Q: Модель не вызывает инструменты. Почему?

**A:** Возможные причины:
1. Модель не поддерживает Function Calling (проверьте через [Lab 00](https://github.com/kshvakov/ai-agent-course/tree/main/translations/ru/labs/lab00-capability-check))
2. Плохое описание инструмента (`Description` неясное)
3. Завышенная `Temperature` (сильно выше диапазона 0.0–0.3)

**Решение:** Используйте модель с поддержкой tools, улучшите `Description`, снизьте `Temperature` (0.0–0.3) и добавьте repair ломаного JSON.

**См. также:** [Глава 03: Инструменты](../03-tools-and-function-calling/README.md#ошибка-1-модель-не-генерирует-tool_call)

SDK **закрытый** (не open-source), поэтому здесь нет ни кода SDK, ни обещаний API: это карта контрактов **по состоянию на октябрь 2026** — чтобы связать принципы курса с тем, как они выглядят в боевом рантайме. ### Карта модулей

| Модуль | Роль |
|---|---|
| `agent` | Цикл `Run`/`Stream`: итерации, события, failover провайдеров, параллельные tools, auto-condense, детект зацикливания |
| `agent/recovery` | Парсеры «протёкших» в текст tool calls (XML/bracket-форматы) — запасной путь, не основной протокол |
| `llm` | Фасад: `Model` (описание модели) → `Open()` → долгоживущий `Client` (Chat/Stream); retry транзиентных ошибок внутри клиента; драйверы провайдеров регистрируются blank-импортом, как `database/sql` |
| `llm/catalog` | Каталог провайдеров и моделей: готовые описания моделей, отдельный пакет, чтобы не попадать в бинарь |
| `memory` | Линейная история сообщений: конкретная структура (Append/Messages/Replace/Snapshot/Restore) со встроенной санитизацией |
| `condense` | LLM-сжатие истории: head → summary с тем же кэшируемым префиксом, tail целиком |
| `tool` | Интерфейс Tool, реестр, типизированный конструктор, опции (read-only/parallel/confirm), StreamingTool, FSHooks-политика хоста, референс-набор tools (read/write/edit/exec/fetch/...) |
| `skill` | Загрузка SKILL.md-скилов (agentskills.io), PromptSection для system prompt, progressive disclosure |
| `genobject` | Structured output: один запрос → типизированный Go-объект (схема из типа, repair ломаного JSON) |
| `schema`, `jsonrepair` | Генерация JSON Schema из Go-структур; устойчивый парсинг ломаного JSON |

### Ключевые контракты

```go
// Цикл: одна функция, конфиг — плоская структура, событий — закрытый набор
func (a *Agent) Run(ctx context.Context, in RunInput) (*RunResult, error)
func (a *Agent) Stream(ctx context.Context, in RunInput) iter.Seq2[Event, error]

type Config struct {
    Resolve   llm.Resolver   // где взять llm.Client
    Memory    *memory.History
    Tools     []tool.Tool
    Prompt    string         // неизменяемый кэшируемый префикс
    Inject    func(LoopState) []llm.Message // динамика: вставка сообщений в ход (интерливинг)
    Stop      func(LoopState, llm.Response) bool
    Confirm   ConfirmFunc    // UX-подтверждение, НЕ security boundary
    Condense  CondenseFunc   // один порог ~0.85, максимум 1 за Run
    Recovery  RecoveryFunc   // парсинг «протёкших» tool calls
    Fallbacks []llm.Resolver // каждый резерв не более 1 раза за Run
    Limits    Limits         // итерации, дедлайн — терминальные границы
    On        func(Event)    // EvDelta / EvResponse / EvToolStart / EvToolUpdate / EvToolEnd / EvCondenseErr / EvDone
    Streaming bool
}

// RunResult возвращается даже при ошибке — частичные данные полезны
```

### Инварианты, которые переживают смену API

1. Один порог condense (~0.85 окна по `usage.PromptTokens`), максимум одно сжатие за Run.
2. System prompt + блок tools — неизменяемый префикс; динамика — через tool results и вставку сообщений в конец.
3. Confirm — UX; граница безопасности — изоляция процесса, права хоста, allowlist.
4. Подтверждение человека — обязательный аргумент инструмента (`confirmed_by`); «подтвердил бот» = отказ.
5. Ошибки: transient → retry в клиенте; loop-limit/дедлайн → терминально + сообщение человеку.
6. Бюджет на результат инструмента (~128 KB) — иначе контекст съедается; у модели — отфильтрованная версия (`FilteredContent`).
7. Скилы вместо каталогов из 20+ tool-обёрток: 10 скилов = ~10 строк префикса.
8. Субагент — тот же цикл с чистой памятью: ревью и вынос шумного чтения, без пишущих внешних инструментов.
9. Ошибки конфигурации (порог вне (0,1), nil-резерв) — на старте, не в проде.
10. Redaction по умолчанию: модель/клиент не попадают в логи с ключами.
